## 一、为什么要做这个

玩家反馈：一局里还是经常撞见同一条主诉。

**而且这不只是"烦"，还是个实验效度问题**：

> 同一条主诉如果在第一轮出现过（**反馈已经把答案告诉他了**），
> 第二轮再遇到，玩家可能是**回忆**而不是**判断**。

数据：现在每档 45 条，标准版一局要抽 30~48 次。
**光靠扩池子有天花板**（45 条 → 重复率仍有 27%）。
**加上"一局内不重复"，重复率降到 0。**

## 二、`js/patient.js`：加 `exclude` 参数

### 接口

```js
PatientGen.generate({ hasSignal, dPrime, rng, exclude })
```

新增第 4 个参数 `exclude`：**一个字符串数组，里面是本局已经用过的那些主诉句子。**

抽主诉时：

1. 按 severity 定出档位（和现在一样）
2. **从该档池子里先排除掉 `exclude` 里的句子**
3. 从剩下的里面随机抽一条
4. **如果排除之后池子空了 → 退回用完整的池子**（不要报错，不要返回空）

**行为约定**：

| `exclude` | 行为 |
|---|---|
| 不传 / `undefined` / `[]` | **和现在一模一样**，不排除任何东西 |
| 有内容 | 排除掉那些句子再抽 |
| 排除后为空 | 退回完整池子 |

### ★ 为什么让调用方传进来，而不是 `generate()` 自己记

**为了让 `generate()` 保持无副作用。**

```
如果让 patient.js 内部自己维护一个"用过的"集合
        ↓
那么【连续生成 5000 位患者】的测试脚本，行为会变
（池子用完了，后面的患者只能重复）
        ↓
之前所有基于"大量生成、看分布"的验证方法全部失效
```

**做成参数传进来，`generate()` 就还是"给同样的输入、得同样的输出"。**

**这一条要写进文件的注释里**，免得以后有人"顺手优化"成内部状态。

### 顺带

`arrival`（来院方式）**不用做去重** —— 它只有 12 条/档，去重做不到，
而且玩家对它的重复不像主诉那么敏感。

## 三、`js/engine.js`：维护"已用清单"

### 要做的

1. **一局开始时**（`Engine.start()`）清空一个 `usedComplaints` 数组
2. **每生成一位患者之后**，把他的 `chiefComplaint` 推进去
3. **调 `generate()` 时**把 `usedComplaints` 传进 `exclude`

### ★ 粒度：一局 = 练习轮 + 正式三轮？

**不要跨练习轮。** 理由：

```
练习轮 12 位 + 正式三轮 90 位 = 102 次抽取
而池子是 45 条/档 —— 总抽取量可能超过池子
        ↓
强行跨局去重会导致【后面的轮次频繁退回完整池子】，反而不稳定
```

**做法**：

- **练习轮开始时**清空一次（练习轮内部不重复）
- **正式第一轮开始时**再清空一次（三轮之间共享一份清单，不重复）

**这样每一段的抽取量（12 次 / 90 次）都在池子容量（45 条/档）的可承受范围内。**

### 验证过的容量数据（供你判断）

```
标准版一局 90 次抽取，跑 5000 局：
  mild   ：池子 45 条，最多需抽 48 次 —— 5000 局里只有 6 局会超池
  mid    ：池子 45 条，最多需抽 43 次 —— 0 局超池
  severe ：池子 45 条，最多需抽 47 次 —— 5000 局里只有 6 局会超池
```

**99.88% 的局完全够用**，超池的那极少数会退回完整池子（行为正确，只是可能重复一两条）。

## 五、自测（★ 按契约 §10 的格式）

### ① 去重真的生效了吗

**完整跑一局标准版**（可以配 `FAST=1`，只要抽取逻辑是真的），收集所有出现的 `chiefComplaint`。

**【测什么】** 一局之内同一条主诉不出现两次
**【期望】** 90 个主诉里，重复的条数 = 0
**【它怎么失败】** `exclude` 没传进去、传了但 `generate()` 没读、
或者清单在每轮之间被清空了（那样每轮内部不重复、跨轮会重复）
**【★ 怎么确认它真的会失败】**
**把 `exclude` 改成永远传 `[]`**（＝退回改动前的行为），
重跑同一局 —— 断言"没有重复"必须红。**把红的那几条重复的句子打出来。**

### ② 不影响原来的行为

**【测什么】** 不传 `exclude` 时，`generate()` 和改动前完全一样
**【怎么测】** 用固定 rng 种子，各生成 200 位患者，比较改动前后的输出
**【期望】** 逐字节相同
**【★ 怎么确认它真的会失败】** 把 `exclude` 的默认值从"不排除"改成"排除空池"，
这条断言必须红

### ③ 池子抽空时的兜底

**【测什么】** `exclude` 里塞满整档 45 条时，`generate()` 不报错、能返回正常患者
**【期望】** 返回的 `chiefComplaint` 是那一档里的合法句子
**【★ 怎么确认它真的会失败】** 把兜底分支删掉（改成返回空串或抛错），
这条必须红

### ④ 分布没被改坏

**【测什么】** 加了去重之后，主诉的档位分布还是原来那样
**【怎么测】** 跑 2000 局完整标准版，统计三档占比
**【期望】** 和改之前一致（信号组大约 mild 15% / mid 26% / severe 59%）
**【为什么这条重要】** 去重如果实现成"排除整档"，分布会立刻塌掉

### ⑤ 提示文案

**【测什么】** 游戏屏上那句提示里**没有方位词**
**【期望】** 文字 = `看清主诉和生命体征，再做判断。`
**【★ 怎么确认它真的会失败】** 纯文案断言，改回去就会红
